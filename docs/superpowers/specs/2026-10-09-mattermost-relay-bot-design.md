# 팀장 채널 → B203 공지 전달 봇 — 설계 사양서

- 작성일: 2026-10-09
- 상태: 설계 확정 (구현 전)
- 대상 서버: `https://meeting.ssafy.com` (SSAFY 운영 Mattermost)
- 팀: `15기 자율 대전2반` (`s15p30b2`)

---

## 1. 목적 (Goal)

팀장만 접근 가능한 비공개 채널(`[자율 2반] 팀장`, `<팀장채널>`)에 올라오는
교육프로·컨설턴트·실습코치의 **공지성 글과 첨부파일**을, 해당 채널에 접근 권한이 없는
팀원들이 볼 수 있도록 **`<팀채널> B203`에 자동으로 복사·전달**한다.

팀원은 원본 채널에 권한이 없으므로, **링크가 아니라 실제 내용(본문 + 첨부파일)을 그대로 복제**해야 한다.

## 2. 핵심 제약 (Constraints)

- 이 서버는 SSAFY 운영 서버로, 일반 계정에 대해 **봇 계정 생성과 개인용 접근 토큰(PAT) 발급이 모두 비활성화**되어 있다. (조사로 확인함)
  - 통합 메뉴: Incoming/Outgoing Webhook, 슬래시 명령어만 존재 (Bot Accounts 없음)
  - 보안 설정: 패스워드·세션 관리만 존재 (Personal Access Token 없음)
  - Outgoing Webhook은 공개 채널 전용이라 비공개 팀장 채널 감지 불가.
- 따라서 비공개 채널을 읽을 수 있는 주체는 **그 채널의 멤버인 사용자 본인(`audguscjf`) 계정뿐**이다.
  → 봇은 **본인 계정으로 로그인**하여 동작하는 self-bot 형태가 된다.
- 자동화 접속에 대한 정책/책임은 사용자가 수용하기로 함. (해당 채널로 인한 불이익 가능성은 낮다고 판단)

## 3. 비목표 (Non-Goals / YAGNI)

- 실시간(초 단위) 전달 — 5분 내외 지연 허용.
- 양방향 동기화, 메시지 수정/삭제 반영 — 하지 않는다. **새로 올라온 글만 단방향 전달**.
- 웹 UI, 관리자 대시보드 — 없음. 설정은 파일로만.
- 여러 팀/반 지원 — 이 팀 전용.

## 5. 아키텍처 (폴링 흐름)

```
[GitHub Actions · 5분 cron]
  → ① 로그인 (Secrets ID/PW → 세션 토큰)
  → ② 각 소스 채널에서 state.json의 마지막 처리 시각 이후 글 조회
  → ③ 발신자가 allowed_senders에 포함된 글만 필터 (시간순 정렬)
  → ④ 각 글: 머리말 포맷 + 첨부파일 다운로드→대상 채널 재업로드 + 본문 전달
  → ⑤ 처리한 글 중 최신 create_at으로 state 갱신 (변경 시에만 커밋)
```

### 설계 원칙: I/O와 로직 분리
- **`mattermost_client`** 는 API 호출(로그인, 글 조회, 파일 다운로드/업로드, 글 작성)만 담당.
- **`relay`** 는 판단 로직(새 글 찾기 → 필터 → 포맷)만 담당하며 외부 I/O는 client에 위임.
- 덕분에 가짜(fake) client를 주입해 **실제 서버 없이 로직 단위 테스트** 가능.

## 6. 구성 요소 (파일)

| `bot/mattermost_client.py` | Mattermost REST API 래퍼 (로그인/조회/다운로드/업로드/작성) |

| `bot/main.py` | 진입점 (1회 폴링 실행, 드라이런 옵션) |

| `requirements.txt` | 의존성 (requests 등 최소) |
| `README.md` | 설치·설정·운영 전환 안내 |

## 7. 설정 스키마 (config.yaml 예시)

```yaml
server_url: https://meeting.ssafy.com
team: s15p30b2
dry_run: true            # true면 전달하지 않고 로그만 출력
source_channels:         # 표시이름 또는 channel name
  - "모의 소스"
destination_channel: "모의 대상"
allowed_senders:         # username 또는 표시이름
  - audguscjf
  - 명현철
poll_overlap_seconds: 5  # 경계 누락 방지용 약간의 겹침
```

## 8. 상태 스키마 (state.json)

```json
{
  "channels": {
    "<source_channel_id>": { "last_create_at": 1760000000000 }
  }
}
```
- 소스 채널별로 마지막 처리한 글의 `create_at`(ms) 저장.
- **변경이 있을 때만** 저장소에 커밋 → 조용한 시간엔 커밋 없음(소음 최소화).

## 10. 자격증명 & 보안

- SSAFY ID/PW는 코드·설정파일에 저장 금지. **GitHub Secrets에만** 보관.
- Secrets는 공개 저장소에서도 노출되지 않음.
- 리스크: GitHub 실행기는 해외(미국) IP → SSAFY 서버가 "낯선 위치에서 반복 로그인"을 이상 접속으로 감지할 가능성. 테스트 중 로그인 차단/경고 발생 시 대응 재논의.

## 11. 오류 처리

- 로그인/네트워크 실패 → 해당 회차 건너뜀, **state 미갱신**(다음 회차 재시도, 누락 없음).
- 첨부 재업로드 실패 → 본문은 전달, 경고 표기.
- 모든 예외는 Actions 로그로 남김.

## 12. 테스트 & 롤아웃 순서

1. 내 PC(conda)에서 **드라이런** — 전달 없이 "무엇을 전달할지" 로그 확인.
2. 비공개 테스트 채널(모의 소스/대상, 멤버 본인+명현철)로 **실제 전달** 검증.
3. 단위 테스트로 필터·중복방지·포맷 검증.
4. GitHub Actions 업로드 후 대상=테스트 채널로 **무인 검증**.
5. 이상 없으면 소스=실제 팀장 채널 2곳, 대상=`<팀채널> B203`으로 설정 전환.

## 13. 위험 요소 (Risks)

- 해외 IP 반복 로그인에 대한 서버 측 보안 반응 (차단 가능성).
- SSAFY 서버 API 버전/엔드포인트 차이 — 구현 시 실제 응답으로 검증 필요.
- 세션 만료/로그인 정책 — 매 회차 재로그인으로 대응.
- GitHub cron 지연·60일 무활동 자동 비활성화 — 상태 커밋/간헐 활동으로 완화.

## 14. 미해결/확인 필요

- 4명 발신자 및 명현철의 실제 username/user_id (구현 초기 해석 단계에서 확정).
- 실제 팀장 채널 2곳의 정확한 channel name/id (운영 전환 시 확정).
